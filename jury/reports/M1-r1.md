### Blocker

<a id="bl-1"></a>
#### BL-1. Детектор исчезновений не срабатывает в реальной синхронизации: снятое с Культура.РФ событие остаётся «по плану» и «проверено только что»

- **Источники:** jury-data, jury-architect, jury-ministry. Три независимых воспроизведения, все скептики подтвердили blocker.
- **Область:** `apps/api/src/modules/ingestion/` — `connectors/culture-ru.ts`, `runner.ts`, `pipeline.ts`.
- **Причина в коде:**
  - `connectors/culture-ru.ts:131-157`: `fetchRegion` дописывает `events/<id>.json` только для событий из текущего списка и никогда не удаляет файлы исчезнувших. В `src` нет ни одного `unlink` или `rm`.
  - `runner.ts:22`: `loadCultureRu` читает все `events/*.json` без сверки с `listed.json`. `runner.ts:25` считает признак `complete` по числу файлов, и устаревшие файлы его только поддерживают.
  - `pipeline.ts:293-303`: для неизменного payload ставится `last_seen_run = runId` и выполняется `UPDATE occurrence SET last_verified_at = now(), freshness = 'fresh'`.
  - `pipeline.ts:511-520`: `finishRun` ищет записи с `last_seen_run IS DISTINCT FROM runId`, а таких не остаётся.
- **Воспроизведение:**
  - Настоящие `fetchRegion` и `loadCultureRu` с подменённым `fetch`, тот же путь, что у задачи `sync-culture-ru` (`main/worker.ts:24-25`). Событие 202 с сеансом через 3 дня убрано из фида. После второго прогона в `events/` по-прежнему лежит `202.json`, `eventsUnchanged=2`, `vanished=0`, сеанс `scheduled|fresh`, `last_verified_at` обновлён до now(), в `change_log` только `created`.
  - Список [101, 102, 103] → [101, 103]: `unchanged=3, vanished=0`, у 102 `last_seen_run=2`, `scheduled|fresh`.
  - Копия рабочей БД: 7347081 убран из `pages/0172.json` (20 → 19) и `listed.json`, файл карточки оставлен. `ingest:load` дал `eventsUnchanged 8541, vanished 0`. Сеанс «Час толерантности «Право быть другим»» 14.11 11:00 остался `scheduled|fresh` с `last_verified_at` = момент загрузки. Второй прогон — тот же итог.
  - Контроль во всех опытах: если удалить файл карточки вручную, детектор срабатывает (`vanished=1`, `unverified|vanished`, паспорт показывает «Информация уточняется»). Сам детектор рабочий, его обходит неочищаемый кэш.
- **Почему blocker:** пользователь видит неверный факт — снятое, возможно отменённое событие «по плану» и «свежеподтверждённое». Нарушены `docs/06-data.md` §7 и §9, детектор исчезновений входит в объём M1 (`docs/11-roadmap.md`). В проде кэш лежит на постоянном томе `rawdata:/data` (`docker-compose.prod.yml:36-37`), дефект проявится со второго цикла синхронизации. Тестов на детектор нет.
- **Что сделать:** множество «увиденных» `external_id` строить по списку текущего прогона. Загружать только перечисленные карточки, остальные архивировать или удалять, чистить `pages/`, `complete` считать по списку, ответ 404 на карточку считать сигналом исчезновения. Интеграционный тест «событие пропало из списка за 3 дня до даты → unverified + запись в change_log + задача модератору».
- **Связано:** MJ-1, MJ-3, MJ-5.

<a id="bl-2"></a>
#### BL-2. Слияние дублей теряет сеансы поглощённого события

- **Источники:** jury-data (blocker), jury-ministry (blocker), jury-architect (major, первая часть замечания «Автослияние дублей прячет сеансы…»; вторая часть — в MJ-8). Итог — blocker.
- **Область:** `dedup/service.ts:63-67`, `organizer/routes.ts:102` (ручное слияние), `catalog/queries.ts:72-80`, `search/service.ts:95`.
- **Причина:** при слиянии выполняется только `UPDATE event SET cluster_id = keep.id, moderation_status = 'hidden'`. Сеансы скрытого события не переносятся и не объединяются. Паспорт скрытого дубля перенаправляется на каноническое событие и показывает только его сеансы, поиск требует `moderation_status = 'published'`.
- **Доказательство на рабочем каталоге:** «Концерт «Наполним музыкой сердца»» (culture.ru 7383783, `01a19c9d-74e3-7092-ae39-94501ede43ef`) слит в `01a19c9d-5706-7f47-9d6f-e77cec127765` со score 0,92, хотя среди причин есть «сильно разные цены». У скрытого события сеансы 05.11 18:00, 11.11 13:45 и 30.11 18:00 в Октябрьском музыкальном колледже, у канонического — только 05.11 и 30.11.
  - `GET /v1/events/01a19c9d-5706-…` → две даты; `GET /v1/events/01a19c9d-74e3-…` → та же каноническая карточка с двумя датами.
  - `GET /v1/occurrences?date_from=2026-11-11&date_to=2026-11-11&q=Наполним музыкой сердца` → `{"items":[],"total":0}`; выборка за 11.11 по `municipality=oktyabrskii` (29 сеансов) его тоже не содержит.
  - Масштаб сейчас: 28 автослияний, 31 будущий сеанс у скрытых событий, у одного нет пары в каноническом событии в пределах ±45 мин. Синтетический сценарий jury-architect: у дубля лишний сеанс через 16 дней, после `runDedup` в поиске видна 1 дата из 2.
- **Почему blocker:** неполное расписание — неверный факт о событии. `docs/06-data.md` §5.2 называет скрытие события «худшей ошибкой», §6 требует собирать золотую запись, а не отбрасывать данные.
- **Что сделать:** сливать на уровне сеансов. Совпавшие (±45 мин, та же площадка) объединять, остальные переносить в каноническое событие с provenance. Слияние и разъединение вынести в публичный сервис модуля `dedup` и вызывать его же из модерации. Тест «слияние не теряет ни одного будущего сеанса».
- **Связано:** BL-3, MJ-8.

#### BL-3. Слияние не учитывает приоритет источников: карточка кабинета скрывается, отмена в кабинете не видна

- **Источник:** jury-data.
- **Область:** `dedup/service.ts:64`, `lifecycle/index.ts:31` (формула `quality_score`), `organizer/status.ts`; правила выживания полей `docs/06-data.md` §6.
- **Причина:** `keep` выбирается только по `quality_score`, `trust_level` и источник не учитываются, формула качества доверие к источнику тоже не учитывает. Статус и дата скрытого дубля на канонический сеанс не переносятся.
- **Воспроизведение** (сценарий 7 присяжного, скептик повторил на отдельной БД): culture_ru «Спектакль «Салават»» 06.11 19:00 и такая же карточка из кабинета. `runDedup` → merged=1 (0,97), карточка кабинета (`official_plus`) получает `hidden`. Затем `changeOccurrenceStatus(сеанс кабинета, cancelled)` → `{status:'cancelled'}`, но `searchOccurrences` на 06.11 отдаёт «Спектакль «Салават» | 2026-11-06T19:00:00+05:00 | scheduled», а `getEventDetail(id кабинета)` ведёт на каноническое событие со статусом scheduled. После `refreshDerived` (оба `quality_score` 0,5) — тот же результат. `runDedup` запускается автоматически после ингеста (`worker.ts:26`).
- **Уточнение скептика:** «побеждает более раннее» верно только при ничьей (id — UUIDv7). Когда у кабинета `quality_score` null или ниже (нет картинок, короткое описание — обычный случай), culture_ru побеждает и без ничьей.
- **Почему blocker:** отменённый спектакль показан как запланированный, ломается демо-сценарий «отмена → уведомление». Нарушен §6 («Статус сеанса: Кабинет учреждения → …», «Дата и время: Кабинет → PRO.Культура»), ADR нет.
- **Что сделать:** золотая запись. `keep` выбирать по уровню доверия (official_plus > official > partner), поля и статусы сеансов брать по таблице приоритетов §6 из всех членов кластера, статус из кабинета переносить на канонический сеанс. Тест «отмена в кабинете на дубле видна в поиске».

#### BL-4. Уведомление о переносе из источника называет неверную исходную дату; источник сдвигает уже перенесённый сеанс

- **Источник:** jury-data.
- **Область:** `ingestion/pipeline.ts:441-453` (`syncSessions`), `notify/service.ts:46-53, 81-92`.
- **Причина:** при переносе из источника `starts_at` меняется в той же строке `occurrence`, а текст уведомления строит «когда» из текущего `o.starts_at` и игнорирует `old_value`. Перенос из кабинета (`organizer/status.ts:38-66`) создаёт новый сеанс, поэтому там текст верный («7 ноября … перенесено на 14 ноября»).
- **Воспроизведение** (скептик, реальная Postgres, временная БД):
  - Сценарий 1: источник перенёс сеанс с 07.11 19:00 на 09.11 19:00. В `change_log` old `2026-11-07T14:00:00.000Z`, new `2026-11-09T14:00:00.000Z`. Подписчику уходит «Перенос: «Спектакль «Тест переноса»» (9 ноября в 19:00, Площадка 1) перенесено на 9 ноября в 19:00.»
  - Сценарий 2: перенос в кабинете, затем источник «догоняет» до 14.11. Уходит второе уведомление «Перенос: «Спектакль «Кабинет»» (14 ноября в 19:00, Площадка 1) перенесено на 14 ноября в 19:00.» Старый сеанс в статусе `rescheduled` сдвинут на 14.11, в БД два сеанса в одно время, исходная дата потеряна.
- **Почему blocker:** подписчик получает неверный факт об исходной дате в ключевом сценарии «изменения в избранном» и бессмысленный дубль уведомления.
- **Что сделать:** для `kind=rescheduled` брать исходную дату из `old_value`. Сеанс в статусе `rescheduled` источником не двигать, а сопоставлять с `rescheduled_to`. Не слать повторное уведомление об уже объявленном переносе. Тест на текст уведомления.

#### BL-6. Машина статусов сеанса не соблюдается: недопустимые переходы, дубли уведомлений, ложное «Билетов нет», фантомные сеансы

- **Источники:** jury-architect (major, скептик повысил до blocker), jury-data (major), jury-ministry (major). Итог — blocker.
- **Область:** `organizer/status.ts:19-94`, `organizer/routes.ts:30-56` (`POST /admin/occurrences/{id}/status`), `lifecycle/index.ts:49`, `notify/service.ts:92`.
- **Причина:** нет таблицы допустимых переходов и проверки «статус уже такой». Ветка `else` (строки 68-78) всегда пишет `change_log kind='status'`. Строка 73-74: `availability: ch.status === "sold_out" ? "sold_out" : occ.availability`. Повторный перенос не проверяет `occ.status`, проверки «новая дата в будущем» нет. Уведомления дедуплицируются только по `(profile_id, change_id)`.
- **Воспроизведение** (три независимых скрипта скептиков на временных БД):
  - Две одинаковые отмены → `change_log n=2`, `processPendingChanges {changes: 2, sent: 2}`; подписчик дважды получает «Отмена: «Буратино» 7 ноября в 19:00, Башкирский театр кукол отменено.»
  - Приняты переходы `cancelled → scheduled`, `ended → sold_out → scheduled`, `rescheduled → cancelled`, `rescheduled → scheduled` (без очистки `rescheduled_to`, исходный и перенесённый сеансы живут одновременно).
  - `sold_out → scheduled` даёт `{status: scheduled, availability: sold_out}`. Веб (`apps/web/src/lib/format.ts:49-53`) показывает «Билетов нет» в карточке, списке сеансов, паспорте и Mini App, `jsonld.ts:63` отдаёт `SoldOut`.
  - Двойной перенос исходного сеанса 07.11 → два сеанса кабинета `scheduled` (09.11 и 10.11). Сеанс 09.11 осиротел и виден в поиске, в сгруппированной выдаче — как ближайшая дата. В `change_log` два противоречивых переноса, подписчики получают оба.
  - Перенос на `2020-01-01T10:00+05:00` принят: паспорт показал сеанс 2020 года со статусом scheduled и запись «Перенесено: 7 ноября 18:00 → 1 января 10:00».
  - `markEnded` переводит `unverified → ended`, такого ребра в диаграмме §7 нет.
  - Актор всех записей — `cabinet:demo` (`organizer/routes.ts:53`).
- **Почему blocker:** после штатного перехода §7 «sold_out → scheduled: билеты вернулись» пользователь видит ложное «Билетов нет», а фантомный сеанс — это выдуманная дата. По `docs/06-data.md` §7 `cancelled`, `rescheduled` и `ended` — конечные состояния, ADR на отклонение нет. Тестов статусов два, только счастливые пути (`test/telegram-and-notify.test.ts:138-187`), а T6 требует «тесты машины статусов». Админ-UI (`apps/admin/src/lib/status.ts`) прикрывает часть путей, но не «восстановить» после отмены, не прямые вызовы API и не двойную отправку.
- **Что сделать:** таблица переходов по §7, ответ 409 на недопустимый переход. Неизменный статус — без записи в `change_log`, приём `Idempotency-Key`. Сброс `availability` при выходе из `sold_out`. Повторный перенос двигает уже созданный новый сеанс. Запрет переноса в прошлое. Актор — из аутентификации (см. MJ-18). Тест на каждый переход, включая запрещённые.

- **Причина:** глобальный хук `onRequest` проверяет сырую строку (`if (!req.url.startsWith("/admin/")) return;`), а маршрутизатор Fastify декодирует percent-encoding и находит маршрут `/admin/...`.
- **Доказательства:**

Токен сравнивать через `timingSafeEqual`. Регрессионные тесты на `/%61dmin`, `/adm%69n`, `//admin`, `/ADMIN` для всех `/admin`-маршрутов.

#### BL-8. IDOR в `/v1/assistant`: по chat_id читается и перезаписывается диалог пользователя бота

- **Источник:** jury-security.
- **Область:** `channels/telegram/bot.ts:50`, `assistant/service.ts:197`, `assistant/routes.ts`, `packages/contract/src/index.ts:312`.
- **Причина:** бот строит `conversation_id = tg-${chatId}`. Публичный `POST /v1/assistant` без аутентификации принимает `conversation_id` от клиента (`z.string().optional()`, `id ?? randomUUID()`) и читает `conv:<id>` из Valkey без проверки владельца.
- **Воспроизведение** (присяжный — :8099, Valkey DB 9; скептик — :8093, Valkey DB 12, отдельный процесс в роли бота): жертва пишет «в Стерлитамаке в субботу с ребенком 5 лет до 500 рублей». Атакующий отправляет только `{"conversation_id":"tg-555000444","patch":{}}` и получает чипы «Суббота, 7 ноября», «Стерлитамак», «ребёнок 5 лет», «до 500 ₽ за билет», в `slots` — `sterlitamak`, `kids_ages [5]`, `budget 500`. `patch {municipality_id:"ufa", kids_ages:[13]}` перезаписал состояние жертвы: следующие подборки бота пойдут из подменённых слотов.
- **Почему blocker:** `docs/09-compliance-security.md` §2.1 относит ID в Telegram и состояние диалога к ПДн; связка с городом и возрастом ребёнка — утечка ПДн. chat_id в личном чате равен Telegram user ID и не секретен. Лимит 20 запросов в минуту адресную атаку не останавливает и сам обходится (MJ-17).
- **Что сделать:** `conversation_id` выдаёт только сервер (128 случайных бит) или клиент присылает токен с HMAC-подписью. Идентификаторы канала во внутренний ключ не входят, клиентские ID с префиксом `tg-` отклоняются. Ключ Valkey привязан к профилю (device или initData). Тест «чужой conversation_id не возвращает чужие слоты».
